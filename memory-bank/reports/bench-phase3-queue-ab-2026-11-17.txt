Phase 3: Queue, back-to-back A/B
=================================
toolchain: go1.27.4
date: 2026-11-17
load: about 200 on 10 cores (heavily loaded), so only interleaved
      comparisons are used (alternating old, new, new, old, ...).
      Every figure is the minimum over 5 rounds of 100 ms. Allocation counts and
      bytes are exact and do not depend on load.

Method
  OLD = HEAD (0033050) in a detached worktree plus the new benchmark files.
  NEW = working tree. Two test binaries built with `go test -c`, run alternately
  by /tmp/ab_queue.py (same script as the Phase 2 reports).
  Benchmarks that read a back-only queue start each iteration from a copy that
  has not been read before (queueWithoutMemo), so a "first read" is measured as
  a first read. The *Reuse and *BackOnly benchmarks read one queue value over
  and over, which is the case the change is for.

What the columns show for a read of a queue that has only a back list
  PeekBackOnly, DequeueBackOnly, IterateReuse: the same queue value read again.
    OLD turns the back list around on every call, NEW does it once and keeps it.
  PeekFirstRead, DrainFromEnqueue, Iterate: a queue nobody has read yet.
    Both turn the list around once; NEW also stores the result, which is one
    extra allocation of 24 B. These stay level, which is the point: the first
    read is not slower, only the later ones are faster.

Reading the table
  - Repeated Peek / Dequeue / Iterate on one back-only queue: 6x to 54,000x
    faster, 0 to 1 allocations instead of one per element (N=10,000: Peek
    142 us -> 2.6 ns, Dequeue 143 us -> 16 ns). This is plan item 3.1.
  - First read of an unread back-only queue (PeekFirstRead, DrainFromEnqueue,
    Iterate): level or 1.02-1.16x faster; one more allocation (the cached copy).
  - Queues that already have a front (DequeueFront, PeekFront, DrainFromSlice,
    Enqueue, EnqueueOne): unchanged within noise.
  - QueueBuilder (3.3): 1.3-1.45x faster to build, allocations halved
    (N=10,000: 20,002 -> 10,013). Bytes at N=10,000 are +4.6% because the
    values are held in a slice while the builder is open.
  - BuildAndDrain (builder, then dequeue everything): 1.54-1.63x faster,
    allocations halved (N=10,000: 40,003 -> 20,013).
  - NewQueueOf / NewQueue (3.2): 1.08-1.14x faster. The intermediate slice
    copy is gone: one allocation fewer and 25% fewer bytes (N=10,000: 321,944
    -> 240,024).
  - Iterator (3.4): 1.14-1.17x faster on a first read, and on a queue that has
    both lists (IterateMixed) 1.07-1.17x faster with 25% fewer bytes.

Cost to know about
  A queue that has been read while it had only a back list now keeps the
  reversed list for as long as it lives, so it holds a second copy of its
  elements (24 B each for a pointer-sized T). That is the price of making the
  second read O(1). Queues built by Enqueue and then only dequeued linearly
  pay it once per version that is read from, and each version's cached copy
  becomes garbage when that version does.

Why the builder collects a slice (3.3) and not the back list
  The plan said "builds the back cons-list directly". That was prototyped
  (a builder that does b.back = cons(v, b.back) and Queue() returning
  &Queue{back: b.back}) and measured against the chosen design, which collects
  values in a slice and builds the front list once. old column below = chosen
  design (front), new column = prototype (back list):

  Building only is 1.45-1.6x faster with the back list, but a queue is built to
  be consumed, and the first read of a back-only queue has to turn the list
  around (N more allocations and 24N more bytes, plus the cached copy). Build
  and drain is 15-18% slower with the back list and makes 50% more
  allocations (30,002 vs 20,013 at N=10,000). The front-list design was kept.
