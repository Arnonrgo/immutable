Phase 4.5: ListIterator keeps the leaf and slot, back-to-back A/B
===================================================================
toolchain: go1.27.4 darwin/arm64
date: 2026-11-17
load: average 165-175 on 10 cores (heavily loaded), so only interleaved
      comparisons are used (alternating old, new, new, old, ...). Every time is the
      minimum over 5 rounds of 100 ms. Allocation counts and bytes are exact.
      Iterate and Contains rows are per whole list (ns, B and allocs per pass).

Change
  Before: the iterator kept a stack of [32] {listNode interface, index} entries
  (768 B, allocated with every Iterator()) and called seek() for every element,
  type-asserting the leaf each time. After: it keeps the current leaf pointer and
  slot, so Next/Prev read a slot and step; the branches above (path [12], 16 B
  each) are used only to move to the next or previous leaf, once per 32 values.
  Contains and ContainsFunc scan a leaf at a time (trieRun) instead of calling
  Next per value.

Method
  OLD = 111c241 (Phase 4.2) in a detached worktree plus the new
  Baseline_List_Iterate benchmark. NEW = working tree. Binaries built with
  `go test -c`, run alternately by /tmp/ab_queue.py.

Result
  Iterate forward / backward, N=1,000 and 100,000: 2.4-2.6x faster
  (about 7 ns to 2.9 ns per value). N=16 (a tail only): 2.8-3.0x, which is the
  iterator's allocation, not stepping.
  Iterator(): 896 B -> 240 B, still 1 allocation.
  Contains with a trie: 3.2x (N=1,000) and 2.3x (N=100,000) faster, 896 -> 240 B.
  Contains on a tail only list: unchanged, 0 allocations.
  BenchmarkList_Iterator Forward / Reverse (one step): 6.8 / 7.0 -> 3.0 ns.
