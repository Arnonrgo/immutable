Phase 2.3: SortedBatchBuilder rewrite, back-to-back A/B
=========================================================
toolchain: go1.27.4
date: 2026-11-17
load: about 200 on 10 cores (heavily loaded), so only same-process, interleaved
      comparisons are used. Every row is min or p25 over 200 rounds (60 from N=10k),
      one GC before each build.

Method
  OLD = HEAD (affbd9b) in a detached worktree; NEW = working tree. Two test
  binaries built with `go test -c`, each running the same TestSortedAB (a
  variant list: SortedMapBuilder as the control, then the batch builder(s)),
  alternated old, new, old, new, old, new; the figures below are the minimum
  over the runs. The control (SortedMapBuilder) is identical code in both trees
  and shows the run-to-run noise (within about 5%).
  Inputs: seq = keys 0..N-1, rand = rand.New(rand.NewSource(7)).Int().
  allocs and bytes are one build measured with runtime.MemStats (deterministic).

Why the first version was replaced
  The first rewrite sorted with slices.SortStableFunc. For random keys it was
  SLOWER than the plain builder (N=100000: 25.5 ms vs 20.3 ms; N=10000: 1.89 ms
  vs 1.40 ms). It now sorts with slices.SortFunc and breaks ties on the
  insertion order (a uint32 seq stored per entry), which gives the same
  last-write-wins result. The tables below are the final version.
