Phase 4.0: List.cap() fix, back-to-back A/B
=============================================
toolchain: go1.27.4
date: 2026-11-17
load: about 200 on 10 cores (heavily loaded), so only interleaved comparisons are
      used (alternating old, new, new, old, ...). Every figure is the minimum
      over 5 rounds of 100 ms. Allocation counts and bytes are exact.

Change
  List.cap() returned 1 << (depth*5) = 32^depth, but a root of depth d covers
  32^(d+1) indexes (a leaf holds 32 values, each level above multiplies by 32).
  append added a root level whenever size+origin reached the under-reported
  value, so every list grown by Append or ListBuilder.Append was one level
  deeper than its size needs (34 values: depth 2, minimal 1; 1,025 values:
  depth 3, minimal 2; 32,769 values: depth 4, minimal 3). The fix is
  1 << ((depth+1)*5).

Method
  OLD = HEAD (7c6be82) in a detached worktree plus the two new AppendBuilt
  benchmarks. NEW = working tree. Binaries built with `go test -c`, run
  alternately by /tmp/ab_queue.py. Lists built by NewList already had the
  smallest depth, so List_Get / List_Set / List_New (rows near 1.0x) are the
  noise control; the AppendBuilt rows, Append and Builder are the ones the fix
  changes.

Reading the table
  - Get on an append-built list: 1.31-1.62x faster (one pointer hop fewer).
  - Persistent Set on an append-built list: 1.33-1.47x faster, one allocation
    and 22-39% of the bytes fewer per Set (N=100,000: 2,624 -> 2,048 B, 6 -> 5
    allocs), because one fewer 576 B branch node is copied.
  - Building by the persistent Append loop: 1.3-1.6x faster, 24-39% fewer bytes
    (N=100,000: 243.9 MB -> 186.3 MB), 17-24% fewer allocations.
  - ListBuilder.Append: 1.3x faster.
  - List_Get, List_Set, List_New and Contains on NewList-built lists show
    0.97-1.22x, which is the noise of this run (the code they run is unchanged).
  - Append at N=100,000 is still 2.4 KB and 4.7 allocations per call; that is
    Phase 4.1-4.3.
